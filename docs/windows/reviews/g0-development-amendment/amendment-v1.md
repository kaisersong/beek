# Windows开发准入补充规则 v1

日期：2026-10-17。原v5方案与签核快照不改写。本补充只调整开发推进依赖，不降低Windows正式验收标准；只有Codex和ZCode明确认可本规则，并完成下述真实G0-D证据，才使用该规则进入G1–G4。

## 已得到的实机事实

用户明确提供ilucas作为可连接Windows机器。已核验Windows11专业版x64 build26300、RTX4090D、控制台session1已登录且桌面可交互；SSH自身是session0，不能充当桌面验收。通过当前用户的Interactive/非提升计划任务在session1执行测试，不靠服务桌面冒充交互桌面。

Windows原型locked debug/release构建、2项Cargo测试、格式检查和20项Python工具测试已通过；Rust1.99.1、MSVC19.50.35726.0、SDK10.0.26100.0及x64 FXC实际记录。所有测试仅使用公开夹具，证据存test-results/ilucas/。

目前debug实机已验证：GPUI正常透明渲染、中文/emoji复制粘贴剪切、Tab、微软拼音候选位置/中文提交，以及非零偏移emoji选区替换为中文。非激活透明窗出现后连续点击10次，记事本前台HWND和焦点子HWND均未变化，Ctrl+C精确复核原选区仍一致。截图及请求/响应保存，未把API签名检查算作实机证明。release构建虽已成功，关键桌面项目仍须在release二进制上重做后才能计入G0-D。

当前只枚举到一块活动1920x1080/96DPI显示器。没有伪造混合DPI/多屏/拔插结果，也不为赶进度安装未签名显示驱动、改系统安全策略或擅自重启Explorer。

## 临时开发门禁G0-D

原18项G0仍为完整G0，其状态不改称通过。新增单独标记的G0-D，仅用于允许G1–G4代码实现和内部预览构建继续：

1. Codex与ZCode对本补充的相同SHA给出明确设计PASS，原方案技术栈/隔离/非激活/安全默认值保持不变。
2. 在真实Windows11 x64 session1、release原型二进制上完成G0-01至11、G0-14、G0-15、G0-17、G0-18这15项。每项仍须实际结果、环境、截图/结构化日志及被测exe散列，不能因本规则而填PASS。截图/自动操作证明对应观察，不凭测试工具自身单测推断产品通过。
3. 若上述任一关键架构前提失败，仍按原G0公开API适配→最小补丁→重审流程处理；不得自动换框架或把关键失败延期。
4. G0-D不是完整G0，也不是G5、正式安装包签核或发布批准。原型debug通过不能替代release路径，尤其Windows release使用预编译HLSL，须实际重测。

## 保留的未执行项目

仅允许把G0-12-DPI（混合DPI/左置副屏）、G0-13-HOTPLUG（真实跨屏/拔插）和G0-16-EXPLORER（真实Explorer重启恢复）保留待执行。前两项当前缺相应活动显示器；第三项按既有手册需要有安排的桌面恢复测试，不由自动脚本在未知用户文件操作期间强杀Explorer。可以补充非破坏性TaskbarCreated消息测试，但必须标明它不能代替真实Explorer重启。

所有原G0项目及上述3项必须在G5签核前补齐真实证据。最终产品还需重做正式UI/IME/焦点、固定L1应用矩阵、完整故障/性能、安装/签名及macOS回归。不能用G0-D生成“完整G0通过”记录，也不能删掉cases.json中的任何必测项或让evidence.py validate/release-gate放宽完整门禁。G0-D另存独立记录，不覆盖完整G0 run.json。

## 开发与发布边界

可推进：平台拆分、core/协议/worker/UI/配置和生命周期代码、自动单测/故障harness、真实单屏Windows内部调试、内部未签名预览。必须继续按实际显示器/DPI查询写实现并保留负坐标/缩放单测，未实测的跨屏行为不得声称已支持。

不可据本规则完成：G5正式签核、对外发布、把未测项写成通过、自动打开G6模拟复制/G7自动安装、隐藏硬件覆盖缺口。源码改变后必须按相应阶段重做证据；最终完整G0–G5聚合门禁继续要求全部87项以及同一冻结源码/二进制的真实证据。

本规则的可接受性判断是：已有实机能尽早证伪GPUI基本可用性，暂缺硬件覆盖仍严格阻止发布，但不使已经验证前提下的内部代码开发无限等待另一块显示器。若复审认为缺少的硬件验证会使某一具体实现步骤不可逆或基本不可行，应给出具体反例并继续修订。
