## 实质问题

### ZCODE-R1-01 · Major · §5.3 / §6.1 / §10.3 — "单次超时 → 结束并重建 helper"把外部慢操作误判为 helper 故障，且 800ms 同时是超时线与 p95 目标

**失败场景**：UIA 跨进程调用慢的常见根因是目标应用忙或其 UIA provider 慢（大文档 Word、挂起中的 Electron 页面），此时 helper 进程本身健康、仍能响应协议。按 §5.3 现行文本"超时先丢弃该请求，再结束并重新创建 helper"，每次超时都触发整进程重建（进程启动 + COM 初始化 + UIA 初始化的代价），重建窗口内的后续请求继续超时，形成正反馈；再叠加"连续三次故障……暂停自动取词"，结果是慢应用的三次划词就把**全局**自动取词停掉，用户切回记事本也取不了词。§6.1 的 `read_clipboard` 与 UIA 查询共用同一 helper 和同一 800ms 预算：外部应用延迟渲染挂起（`OpenClipboard` 成功但 `GetClipboardData` 等待源进程渲染）会同样触发整个 UIA helper 重建并丢失 `TextSelectionChanged` 订阅，剪贴板故障传染取词主路径。另外 §10.3 性能目标 p95 ≤ 800ms 与超时线同值：超过 800ms 的请求不再是"慢成功"而是"失败 + 触发重建"，若这 5% 集中在特定应用，这些应用永远取词失败且持续制造重建。

**最小修正**：在 §5.3 区分两类超时——(a) 协议活性超时：helper 对 ping/控制消息无响应，才杀进程重建；(b) 单请求操作超时：helper 仍响应控制消息，仅丢弃该请求，卡死的 MTA 线程按泄漏阈值计数，达到阈值才重建。`read_clipboard` 的超时与线程隔离单独规定，不与 UIA 查询共享重建判定。重建/退避恢复后由状态机重放当前前台源的订阅。性能章节明确超时线与 p95 目标的数值关系（超时线应高于 p95 目标，或显式声明边缘请求一律快失败且不计入 helper 故障）。

**可检验关闭标准**：helper 故障测试新增两个用例并通过——(1) 模拟目标应用 UIA 挂起连续 ≥3 次：helper 不因单请求超时重建，健康应用（记事本）取词成功率与延迟不回退；(2) 模拟剪贴板延迟渲染挂起连续 ≥3 次：UIA 订阅不丢失、取词不受影响。§10.3 补一句超时线与 p95 的关系声明。

### ZCODE-R1-02 · Major · §3 / §7 / §11 — G0 门禁不含"可激活窗口 + 文本输入 + 中文 IME"验证，设置窗口的架构级风险后置到 G3，且 G3 没有失败处理路径

**失败场景**：GPUI 0.2.2 的 Windows 后端在非激活窗口、透明、托盘方面由 G0 验证，但方案中首个**可激活的文本输入窗口**（设置窗口，含 API Key、base_url、提示词编辑）出现在 G3，而 §7 要求它"支持键盘导航、中文 IME、粘贴、缩放"。Windows IME/光标/焦点在 GPUI 该版本的成熟度是独立的风险区，macOS 可用不能外推。若 G3 才发现 IME 缺陷，fallback 到 Win32 原生编辑控件将违反 §3.4"仅系统必要界面使用 Win32"的边界——这正是 G0"公开 API 调整 → 窗口样式适配 → 可审计最小补丁"路径应提前拦截的架构级返工。同时 §11 只有 G0 写明了失败路径（"失败则修订架构重审"），G3 行没有等价语句，IME 失败时实施 AI 没有既定的升级路径。

**最小修正**：G0 原型增加一项验证：可激活 GPUI 窗口 + 文本输入控件 + 中文 IME（切换输入法、组合窗口跟随、粘贴）冒烟；或在 §4/§7 明确文本输入控件的 Win32 fallback 契约并把它计入"系统必要界面"定义。G3 完成条件补"失败则按 G0 同款路径重审"。

**可检验关闭标准**：G0 证据集中包含真实桌面上中文 IME 输入的录屏或明确记录的 fallback 决策；G3 完成条件文本引用该结论。

### ZCODE-R1-03 · Major · §1 / §7 / §10.3 — 无边框全屏（浏览器 F11、PPT 放映、全屏 PDF）场景的弹窗行为无契约，应用矩阵无用例，G5 发现不了此类失败

**失败场景**：§1 排除的是"游戏和独占全屏"，但浏览器 F11、PowerPoint 放映、全屏 PDF 阅读是普通桌面最常见的查词场景之一，不在排除清单内。§7 只写"处理全屏、锁屏和虚拟桌面边界"，未定义行为：前台为全屏窗口时小蜜蜂是否显示？置顶弹窗显示在无边框全屏之上是否引发焦点抢夺或闪烁？用户退出全屏后已显示的弹窗是否悬挂？§10.3 矩阵没有全屏用例，G5 硬门槛是"普通网页"——按现行 gate 结构，这类失败既不会被测到，也没有契约可判对错。

**最小修正**：§7 增加全屏行为契约（例如：检测前台窗口覆盖目标显示器工作区 → 不显示小蜜蜂并在托盘提示，或明确允许显示并规定焦点行为）；§10.3 矩阵增加"Edge F11 全屏网页 + 一款放映模式应用"一行，含预期/实际记录。

**可检验关闭标准**：修订后的 §7 有可判定的全屏行为定义，且矩阵新增行有对应实测记录要求（首版发布前填写）。

### ZCODE-R1-04 · Minor · §9.1 — 未把"每个公开发布版本必须携带 macOS 通用资产"写成发布纪律；老 macOS 客户端在 Windows-only 版本上会收到虚假更新信号

**失败场景**：核对 `src/update.rs:70-72` 与 `src/update.rs:130-146`：现有 macOS 更新器按精确资产名 `BeeK-v<版本>.zip` 构造 URL 探测，不会误取 `BeeK-v<V>-windows-x64.zip`（方案担心的"误取 Windows 包"实际已被精确命名排除）。但 `check()` 取 atom 的第一个 release（`src/update.rs:161-205`）：若未来发布一个仅含 Windows 资产的版本，老 macOS 客户端会判定"有新版本"且资产探测 404，落入"有更新但只能手动下载"的提示，用户到发布页却找不到 mac 包。§9.1 说"保留既有资产"，但没有把"每版本必须同时发 macOS 资产"写成硬性发布纪律，也没有把该降级提示定义为可接受行为。

**最小修正**：§9.1 补一条发布纪律：每个正式版本必须同时携带 `BeeK-v<V>.zip` 与 DMG；若允许平台单侧发版，需写明老客户端的预期提示行为并加入 §10.2 更新测试。

**可检验关闭标准**：方案文本含该纪律；更新测试表包含"仅 Windows 资产的 release"用例（断言不误报可安装更新、不误取资产）。

### ZCODE-R1-05 · Minor · §8 — 第二实例激活 IPC 与 `--restart-parent` 握手端点的机制、命名、ACL、消息类型表未定义

**失败场景**：§8 用了相当篇幅设计重启协议（PID/创建标识核验、预就绪回执、抢锁失败处理），但其承载通道"当前用户私有握手端点"没有任何机制定义；"第二次启动激活设置或托盘"的通道与"IPC 仅限当前用户，验证请求类型"同样停在约束层。同用户其他进程抢占命名端点（squatting）时重启握手静默失败；消息类型不枚举则"验证请求类型"不可实现也不可测。失败是安全的（旧进程保留），但功能失效且验收无对应用例。

**最小修正**：§8 补一小节：通道类型（命名管道或 HWND 消息）、命名规范（含用户 SID）、DACL（仅当前用户）、允许的消息类型枚举与未知类型一律拒绝。

**可检验关闭标准**：§10.2 生命周期测试增加"端点被抢占/伪造、未知消息类型被拒"用例并通过。

### ZCODE-R1-06 · Minor · §11 — G2 完成条件"记事本/浏览器 L1 实测"早于任何 UI 存在，验收载体未定义

**失败场景**：图标与弹窗在 G3 才实现，G2 阶段的"L1 实测"没有可观察载体——实施 AI 可以用"结构化日志打印取到文本"充当实测通过，这恰是 §11 自己禁止的"以工具调用成功代替验收"。G5 硬门槛虽会最终兜底，但 G2→G3 的交接质量失去判据。

**最小修正**：明确 G2 的验收载体（例如临时诊断面板或固定用例脚本 + 结构化断言输出），写入 G2 完成条件。

**可检验关闭标准**：G2 交接物包含按该载体执行的记事本/Edge/Chrome 用例记录，格式与 §10.3 证据要求一致。

### ZCODE-R1-07 · Minor · §2 / §8 — Windows 无崩溃自动恢复，与 macOS（launchd KeepAlive）的语义差异未声明为取舍

**失败场景**：`src/menubar.rs:283-286` 表明 macOS 重启乃至崩溃均由 launchd KeepAlive 拉起；Windows 首版只有显式 `--restart-parent` 与登录自启动，主进程崩溃（GPUI 渲染线程 panic 等）后托盘消失且无拉起机制。方案未声明这是接受的取舍还是待补能力，§8"无窗口常驻"验收是否隐含崩溃恢复存在歧义。

**最小修正**：§8 明确声明：首版崩溃后不自动恢复，用户下次登录/手动启动；如需崩溃提示（如下次启动检测到异常退出）列为后续能力。

**可检验关闭标准**：方案文本含明确声明，验收表"常驻"定义不再隐含崩溃恢复。

### ZCODE-R1-08 · Minor · §6.3 / §8 — "取消请求"语义不统一，慢请求占满执行槽后的用户可见路径二选一未定

**失败场景**：§6.3 明确复用 blocking 翻译代码、slot 在真实 HTTP 工作结束后才释放（即不存在真取消，只有 generation 过期），但 §8 退出流程写"取消请求"，读者会理解为可中断的 abort。行为后果：两个 60 秒慢流占满执行槽时，用户第三次点击只能进"最新待执行"槽，§6.3 写"显示等待**或**允许替换未开始请求"——两个选项的用户体验完全不同（最长等待 60 秒 vs 立即替换），实现者二选一即产生契约歧义。

**最小修正**：统一措辞：全文区分"中断网络请求"（首版不支持）与"generation 过期丢弃结果"；§6.3 在"显示等待"与"替换未开始请求"中指定首选行为及等待态的 UI 反馈要求。

**可检验关闭标准**：§10.2 翻译测试的"两个长期慢流 + 一个待执行替换"用例断言指定的那个行为；方案文本无"取消请求"歧义表述。

## 赞同点

1. **故障隔离架构正确**：UIA 独立进程 + Job Object + 有界帧协议 + 握手 token + 断管等同可恢复故障（§5.3），是不引 UI 运行时前提下合理的隔离强度。
2. **选区身份设计扎实**：SourceToken 含 `process_created` 防 PID 复用；selection_epoch 区分"同一 HWND 不同文档"；点击小蜜蜂用缓存 + 异步复查、不重查 BeeK 自身、复查期间不发模型请求（§5.1）——选区过期这条链闭合得比多数同类方案好。
3. **返回类型不撒谎**：过期/空/受保护/不支持/超时是不同返回类型，禁止 Value/整页文本冒充选区（§5.2），直接堵住"错误翻译源"这一 Blocking 级风险。
4. **剪贴板设计克制且诚实**：只读路径绝不 `EmptyClipboard/SetClipboardData`、读取下沉 helper 隔离延迟渲染、sequence 复核、明确声明 owner 不能证明数据最初生产者（§6.1）；自动 Ctrl+C 全部默认关闭并设独立门禁（§6.2）。
5. **凭据链完整**：Credential Manager 优先、迁移"先确认保存成功再删明文"、CredentialResolver 优先级链、请求级配置快照冻结避免三次 load 混用（§8）。
6. **坐标/DPI 与历史坑对应**：虚拟桌面物理坐标、保留负坐标、按显示器分别换算、明令禁止复用主屏高度翻转（§7）——与 `src/main.rs:473-483` 注释记录的早期翻转事故吻合，说明方案作者真读过代码。
7. **背压诚实**：承认 blocking 翻译代码不可中断，用执行槽 + 待执行槽 + "SSE 帧上限在读取过程中执行"（§6.3）而非假装能取消。
8. **gate 不易被绕过**：G0 失败路径明确且禁止擅自换 UI 栈；G5 硬门槛禁止把失败应用降标 L2 后仍宣称通过；公共 runner 不得冒充真实桌面证据；应用矩阵要求实测 + L1/L2 标注、禁止用模型推断冒充测试（§3/§10/§11）。
9. **§12 评审规则**不把沉默当同意、禁止同一模型扮演多方——与本次独立评审的立场一致。
10. 本地代码证据表抽查全部属实（`Cargo.toml:13`、`.gitignore:2`、`src/config.rs:66-69`、`src/main.rs:461`、`src/main.rs:1108`、`src/menubar.rs:283-286`、`src/update.rs:70`），且对 `update.rs` 资产机制的担忧经代码核实后我主动收窄为 R1-04 的 Minor，未保留臆测的 Major。

**结论**：REVISE。关闭 ZCODE-R1-01/02/03 后（其余 Minor 可并行修订），本方案具备进入修订轮与实机 gate 的条件。
