# xiaok 本次评审调用的实际诊断

## 模型与调用方式

- 实际模型标识：`qwen3.8-flash-next`，沿用 xiaok 默认配置。
- 原始调用：`xiaok chat --auto --print <prompt>`。
- 后续隔离诊断：直接使用本机安装包的原生 adapter；没有换模型，没有修改全局配置或已安装程序。
- Kimi 的 403 配额问题与此无关，不能拿它解释 xiaok。

## 已确认的三层问题

1. **实施意图误判**：第一次 CLI 会话把只读评审判成 single_stage 的“修订业务代码”；第二次将被评材料拆成多阶段“生成业务代码/生成扩展方案”等。材料应作为待审数据，而不是新的实施任务。
2. **输出和诊断过粗**：`--print` 等整轮结束才输出最终 text。最初的 120/240 秒外层时限没有区分 thinking 和停滞，不能据此断言模型完全没响应。
3. **长流未正常结束**：进度感知的完整 v2 调用持续约300秒，收到5,639个thinking事件、32,113个思考字符、0个最终正文字符，然后上游流结束而没有正常finish边界，adapter 报 `ERR_STREAM_PREMATURE_CLOSE`；`timed_out:false`，未触发我设定的60秒无事件或15分钟总超时。见 `round-2-xiaok-stream-run.json` 与进度 JSONL。不能据此单独断定究竟是网关固定上限、后端模型还是服务端流协议问题；还缺对应网关/服务端日志。

## 复测

- 短请求原 smoke 在3.2秒完成。
- 增加原始包与adapter事件计数的20秒诊断：短请求 HTTP200、约7秒首包、约9.2秒完成；§5评审 HTTP200，20秒时292个数据包、848个思考字符、0正文。证实客户端能够接收并产出thinking事件，不是所有响应都被丢掉。
- 对 v4 按次请求 `enable_thinking:false` 后，45秒仍观察到1,830个思考字符、0正文，按“非思考模式未被兑现”停止。这个参数在当前链路的效果不符合预期，不能宣称已经关闭了实际推理；没有因此改全局配置。
- [阿里云官方文档](https://www.alibabacloud.com/help/en/model-studio/deep-thinking)说明部分Qwen混合思考模型可按次切换，但本机自定义网关是否支持该模型标识与该参数，必须以实际返回为准，不能由官方示例外推。

## 结论与后续定位点

本次没有获得 xiaok 的有效完整评审，不能把thinking文本或调用成功当成审查同意。真正需要进一步定位的是：网关对非标准思考参数的转发、约300秒终止的原因，以及提前EOF时的服务端错误/结束协议。若未来修 xiaok 客户端，应同时改进quoted材料的意图分界、print模式的进度提示与thinking-aware超时诊断。
